# 开拍小笺｜AI 与内容创作

## 1. 一句话产品与具体场景

开拍小笺帮助独立经营咖啡店、自己负责店铺短视频的店主，在每天营业结束后，将三张已有照片和确认过的商品事实，整理成可编辑、可局部改写的 15 秒拍摄脚本，解决“有素材，却不知道先说什么、怎么拍”的问题。

具体场景：一家独立咖啡店的店主，白天在做咖啡、服务客人时拍下成品、制作和店内环境；打烊后想发一条介绍燕麦拿铁的视频。手里有照片，但既不想写成生硬广告，也不想为了改开头反复重做整篇文案。示例中的商品、28 元和特点均为虚构演示资料，不对应真实商家。

这里选择的是“有素材、有表达意愿，但缺少稳定组织方法”的店主，不是完全没有素材的人，也不是已有专业拍摄团队的连锁品牌。值得解决的原因是：创作起点可能卡在组织表达，而不是缺少更强的生成模型。这个判断来自任务拆解与产品推演，目前没有访谈或真实经营数据支持，属于待验证假设。

## 2. 可演示流程

1. 进入：无需登录，在首页选择“咖啡店示例”或自己的照片。
2. 整理：准备成品、制作、环境三份素材，标记用途；填写商品名称、可选价格与确定的特点，选择目的和语气。
3. 确认：先展示创作依据，用户确认后才生成；价格为空就不提价格，未知折扣、地址、功效不自动补充。
4. 生成：显示可取消的加载过程。演示设置可稳定触发一次失败，失败保留输入，重试恢复正常。
5. 修改：输出开头、中段、结尾，每段显示素材、口播和拍摄建议。可直接编辑、只改写一段或撤回，不影响其他段落。
6. 完成：分镜预览检查画面与文字对应关系；保存本机草稿、复制口播或下载文本小笺，交给拍摄/剪辑环节，再做下一条。

边界：本地规则模拟 AI，无真实模型、图像识别、语音或自动剪辑；15 秒只是拍摄节奏参考。照片仅在当前页面会话保留；保存草稿后刷新可恢复文字，自己的照片需要重新选择。示例插画可恢复。不会自动发布。

## 3. 产品判断

**为什么是这个人、这个场景？** 同一位店主同时承担经营和表达，已有照片、商品事实和明确受众，输入足够具体，可以在一个小闭环内检验“脚本是否更容易拍”。场景可重复，但频率和需求强度尚未验证。首轮不泛化到所有内容创作者。

**最核心的问题是什么？** 把“手上真实有什么”与“下一步具体怎么表达”连接起来，而不是批量生成更多文案。

**为什么先确认再生成？** 店主比模型更了解价格、原料和承诺。前置确认把事实与表达分开，也让每段脚本有可用素材。选择局部改写，是为了保留用户已经满意的内容、减少反复全量生成的不确定性。确认环节也会增加操作成本，需要实际观察收益是否超过负担。

**主动不做什么？** 不做一键剪辑、配音和平台发布：它们会引入节奏、音轨、版权和平台适配问题，掩盖本题要验证的“从素材到可执行表达”。不做账号、团队协同、批量营销和复杂 Agent 编排：首轮核心任务不依赖它们。原型只支持三种素材用途，不声称已适配其他行业。

**只能留一个功能？** 保留“每段绑定素材的可编辑拍摄脚本”。事实确认与局部改写围绕这个结果服务；即使去掉分镜预览，用户仍能拍出内容。

**最可能失败在哪里？** 店主真正需要的可能是直接得到成片，不愿再拍或剪；固定三段也可能让内容同质化。其次，生成文案可能过于广告化、对口播时长估计不足，或确认事实的成本高于手写。

**如何证伪？** 找 5 位确实自己经营内容的店主，让他们带真实素材分别用现有方式和原型完成一份拍摄脚本；交替使用顺序，记录从素材到可用稿的时间、人工修改内容、未提供事实被写入的次数，以及是否实际拍摄。随后观察一周是否自发再次使用。若大多数人只想要成片、不采用脚本，就停止增加文案功能，重新验证输出形态。5 人是探索样本，不能据此声称市场成立；不预设转化率或效率提升数字。

## 4. 我最满意的产品/功能：立行的可观察执行与局部恢复

我最满意的产品是自己从 0 到 1 开发的“立行”Multi-Agent 智能旅行规划系统。其中我最喜欢的，是让复杂规划过程可观察、发生问题后能局部恢复的执行机制。这份表述以我的项目开发资料为基础，重点是开发与验证经历，不包装成已经规模化上线的商业产品。

我会在项目开发与回归测试中使用这套机制，检查系统如何把旅行需求分解、调用工具、组合结果，并处理外部工具失败。旅行规划需要同时维护时间、预算等约束；如果只在最后给出一篇完整行程，我很难判断等待发生在哪里，也很难定位某个错误影响了哪部分结果。

让我觉得好的设计不是“多个 Agent 一起工作”本身，而是进度与恢复形成了闭环：系统通过 SSE 流式展示模型输出和工具进度；通过分阶段 Trace 帮助定位问题；对工具失败进行重试，必要时局部 Replan；关键状态由 Checkpoint 留存，支持中断恢复。简历中的 Benchmark 与 Badcase 回归是我验证这些链路的方式，这里不额外编造一次具体旅行或用户反馈。

这个设计有效，是因为它把一次不透明的长等待拆成可以理解和排查的过程。局部失败有机会在受影响的范围内处理，既有结果不用在每次异常后全部重做；但这依赖状态、约束和恢复边界正确，并不是任何失败都能自动修复。

如果只能改一个地方，我会把技术进度进一步转成用户能采取行动的里程碑：哪些条件已经确认、哪里还待核实、某次重规划影响哪一天，并让用户选择“只改这一天，保留其他安排”。这能把执行可观察性变成用户控制感。这个想法也影响了本次 Demo：不满意开头时只改开头，不让满意的两段一起变化。

## 5. AI 使用说明与交付

使用工具：Codex。它参与需求拆解、场景提案、产品判断初稿、界面与交互代码、原创 SVG 示例、说明文档、测试脚本及实际验证。浏览器自动化、PDF 排版工具是执行工具，不作为额外 AI 模型。没有调用真实生成模型，没有使用外部图片生成服务。

人提供的内容：作业要求、交付仓库、个人简历，以及“第一个多 Agent 项目最满意”的偏好。立行的项目经历与机制来自本人资料。用户场景和取舍由 Codex 提案；候选人已明确确认独立咖啡店主场景，并选择优先做好事实确认与局部改写，不做一键成片；没有虚构候选人独立完成的用户调研或手工设计过程。

AI 初稿的问题及修改：初版图片读取存在异步覆盖风险，增加素材位版本检查；补充用途重复校验；草稿恢复需要限制数据结构并说明本地照片不会恢复；分镜可能被误认为成片，明确增加“无音轨、非剪辑成片”标识；用“未提供就不生成价格”的检查约束输出。界面截图与浏览器回归用于验证，而不是把生成成功当作交付完成。

交付内容：5 页产品 PDF、无需登录的静态 Demo、带讲解字幕的 2—3 分钟实际操作视频、可编辑说明与单独 AI 使用记录。在线入口、视频及运行说明见仓库 README；完整验证记录见 output/verification.json。文档不公开简历原件或个人联系方式。
